# 03 — Project Format, Catalog, and Round-trip

## Source of truth

The **editor project file is the single source of truth**:

```
src/campaigns/<campaignId>/
  campaign.editor.json     <- editor's document (what the editor reads/writes)
  campaign.ts              <- generated (v1 output, see 04)
  dungeons/<id>.ts         <- generated
  translations/en.json     <- generated
  translations/sv.json     <- generated
  logs.en.json / logs.sv.json  <- generated (present only if the project defines log keys)
```

Rationale: campaigns contain real code in places (custom item effects,
event handlers). The project file covers the data-only subset; generated TS
must therefore be **overwrite-safe** and never the input of an edit cycle in
v1. Hand edits to generated files are discarded on the next generation — this
is a documented, deliberate trade-off.

## `campaign.editor.json`

Format: JSON via kotlinx.serialization, pretty-printed, UTF-8, LF line
endings, trailing newline.

```jsonc
{
  "formatVersion": 1,
  "campaign": {
    /* CampaignDoc, see 02 */
  },
  "dungeons": [
    /* DungeonDoc, see 02 */
  ],
  "translations": {
    /* TranslationsDoc, see 02 */
  }
}
```

- `formatVersion` gates migrations: on load, unknown **higher** version ->
  error dialog ("project was saved by a newer editor"); lower -> run
  registered migrations sequentially before use.
- Unknown JSON fields must not fail the load (configure
  `ignoreUnknownKeys = true`); the editor rewrites the file in its current
  schema on save.
- Saving is atomic: write to `<file>.tmp`, then move over the target.

## Generated-file protection

Every file the generator writes starts with this exact marker comment:

```ts
// GENERATED FILE - DO NOT EDIT. Source: campaign.editor.json (Drakriddarna Campaign Editor).
```

Before overwriting an existing file the generator checks:

1. File missing -> write it.
2. File starts with the marker -> overwrite.
3. File exists without the marker -> **abort generation** and return an
   error (`"dungeons/e1m0.ts was modified by hand or was not generated by
the editor"`). The UI offers: show the file, or confirm a force overwrite
   after an explicit typed confirmation.

## Shared-content catalog

Items, monster types, and enum vocabularies live in the game repo and are
referenced, not duplicated (02). The editor consumes a **catalog snapshot**:

```
editor/app/src/main/resources/catalog.json
```

### Shape

```jsonc
{
  "version": 1,
  "generatedFrom": "game repo commit <sha>",
  "items": [
    {
      "id": "sword",
      "kind": "weapon", // weapon | armour | shield | magic | monster
      "nameKey": "...", // existing translation key if any
      "amountInDeck": 3,
      "import": { "module": "items/weapons", "export": "weapons", "index": 0 }
    }
  ],
  "monsterTypes": [
    {
      "id": "ORC",
      "import": { "module": "types", "export": "MonsterType", "member": "ORC" },
      "stats": { "health": 2, "defense": 0, "experience": 1 }
    }
  ],
  "interactableEffects": ["toggleLight", "openDoor", "..."],
  "eventNumbers": [1, 2, 3],
  "enums": {
    "Colour": ["Red", "Yellow", "Green", "Blue"],
    "Side": ["Up", "Down", "Left", "Right"]
  }
}
```

The `import` triple is what the generator needs to emit a reference such as
`magicItems[4]` or `MonsterType.ORC`. `stats` exist only to render informative
tooltips/cards in the UI.

### Producing the catalog

A companion script in the **game repo** exports it, so the game's own
TypeScript modules are the authority (never hand-edit `catalog.json`):

```
scripts/export-editor-catalog.ts   # game repo
```

Run with the repo's tooling (`npx tsx scripts/export-editor-catalog.ts >
<editor>/app/src/main/resources/catalog.json` or a vitest wrapper). The
script imports `src/items/*`, `src/monsters/*`, `src/events/*`,
`src/interactables/*` and dumps the shape above. It is small, has no
dependencies beyond `tsx`, and is the only game-repo addition the editor
requires (scripts/ is not part of the shipped game).

The editor UI has a **Refresh catalog** command: path to game repo ->
instructs the user to run the script (v1 may also shell out to it if `tsx`
is available, but must not fail silently if it is not). Bumping the catalog
increments `version`; project `CatalogRef.version` values older than the
current catalog are fine (ids are stable), but references whose `id` no
longer resolves are validation errors (07).

## Round-trip policy

| Direction                         | v1 support                                                                                                                                                                |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Project -> TS files               | Yes — full, deterministic (04)                                                                                                                                            |
| Project -> back into editor       | Yes — save/load `campaign.editor.json`                                                                                                                                    |
| TS files -> project               | **No.** Generated files are output only.                                                                                                                                  |
| Hand-authored campaign -> project | **No (v1).** Future phase: a literal parser for `defineDungeon({...})` inputs. Feasible because hand-authored dungeons use the same declarative subset, but out of scope. |

Because TS -> project is unsupported, the editor's "Open campaign" command
opens a campaign by locating `campaign.editor.json`. If the folder has TS
campaigns but no project file, offer "Start a new project here" (which will
refuse to overwrite the existing files without force confirmation, per the
marker rules above).

## Concurrency and safety

- The editor takes no locks; if `campaign.editor.json`'s modification time
  changed since load at save time, warn before overwriting.
- Generation only writes files inside the chosen campaign folder; it never
  deletes files. Removing a dungeon from the project leaves a stale
  `dungeons/<id>.ts` behind — generation must report stale generated files
  (present with marker, not referenced by the project) and offer to delete
  them after confirmation.
